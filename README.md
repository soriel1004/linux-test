# 우분투 5포트 장비: 카메라 없이 LAN 검사하기

스핀센서 1대와 VISION센서 2대를 각각 기가비트 LAN에 직결하고, 다른 LAN으로 선별용 PC와 연결하는 제품을 위한 입고 검사 도구입니다. 보고된 증상은 **카메라 3대가 동시에 끊기고, 재부팅 후 잠시 연결됐다가 다시 끊어짐**입니다. 카메라 없이 입고된 경우를 기본 검사 시나리오로 합니다.

**카메라 없이도 포트·케이블 경로의 송수신 불량, 링크 단절, 드라이버 리셋, 장시간 부하 이상을 찾을 수 있습니다. 통과 결과는 해당 조건에서 이상을 관측하지 않았다는 뜻입니다. 카메라를 포함한 제품 전체가 정상이라는 보증은 아닙니다.**

이 저장소에는 Python 3.8 이상과 표준 라이브러리만 사용하는 도구 두 개가 있습니다.

| 파일 | 기능 | 카메라 필요 |
|---|---|---|
| `wire_test.py` | 두 LAN 포트를 케이블로 직접 연결해 양방향 프레임 송수신·손실·링크 검사 | 아니요 |
| `lan_diag.py` | 장시간 NIC 오류·드롭·커널·CPU·메모리·온도 기록, 선택적 Ping/TCP/영상 heartbeat 확인 | 아니요. 실제 카메라 응답 검사는 필요 |

## 1. 준비와 포트 확인

준비물은 입고 장비, 정상 확인된 Cat5e 또는 Cat6 케이블 1~2개, 로컬 화면·키보드입니다. 포트는 P1~P5로 표시하고, 우분투 인터페이스 이름과 실물 위치를 대응시켜 기록합니다. 외장 PC가 있으면 독립된 상대 장비로 추가 검증할 수 있습니다.

```bash
cd /path/to/linux-test
python3 --version
python3 lan_diag.py inventory
ip -br link
ip -br address
```

`enp1s0` 같은 이름이 실제 LAN 포트 이름입니다. 아래 모든 예시의 인터페이스 이름을 실제 값으로 바꾸세요. `inventory`는 현재 이름과 상태를 출력하며 설정을 변경하지 않습니다.

기본 수집은 Python만으로도 가능하지만, 상세 정보와 커널 로그 확인을 위해 우분투의 다음 패키지를 권장합니다. `iproute2`는 `wire_test.py` 사전 검사에 필수이고 `ethtool`은 상세 NIC 통계 수집에 권장합니다. `ping`은 카메라/PC 대상 검사를 선택한 경우에만 필요합니다.

```bash
sudo apt-get update
sudo apt-get install -y python3 iproute2 ethtool iputils-ping
```

장비를 가동 중인 생산 라인과 분리하고 콘솔에서 검사하세요. **관리 접속·선별 제어에 사용하는 포트를 시험 포트로 사용하지 마세요.** 도구는 IP·라우팅·MTU·EEE·오프로드를 자동 변경하지 않습니다. `wire_test.py`는 기본 경로가 있는 포트와 브리지·본딩 소속 포트를 거부하지만, 모든 원격 관리 경로를 판별할 수는 없습니다.

## 2. 카메라 없이 검사하는 순서

### A. 장시간 기록부터 시작

아래 명령은 24시간 동안 다섯 포트를 기록합니다. 센서나 케이블이 연결되지 않은 포트의 `carrier=0`은 그 자체로 불량이 아닙니다. 이 상태에서는 부하 송수신 검사가 되지 않습니다.

```bash
sudo python3 lan_diag.py monitor \
  --interfaces enp1s0 enp2s0 enp3s0 enp4s0 enp5s0 \
  --duration 86400 --output ./lan-diag-logs
```

이 명령은 터미널을 계속 사용합니다. 케이블 시험은 다른 터미널에서 실행하세요. 중단은 Ctrl+C 또는 SIGTERM을 사용합니다. 기본 모드는 ICMP/TCP 패킷을 보내지 않습니다. 커널 로그 접근 권한이 없거나 도구가 없으면 해당 항목은 수집 불가로 남으며 정상으로 간주하지 않습니다. 프로그램 시작 시와 종료 시 NIC 설정·라우팅·상세 통계 스냅샷도 저장합니다.

### B. 포트 두 개를 케이블로 직접 연결

예: P1 ↔ P2, P3 ↔ P4를 정상 케이블로 연결합니다. 스위치나 카메라는 필요하지 않습니다. 대부분의 기가비트 포트는 Auto MDI-X로 일반 패치 케이블 연결을 지원합니다. 케이블·포트 사양에 따라 링크가 잡히지 않으면 정상 PC를 상대 장비로 사용하거나 사양을 확인합니다.

연결 뒤 1000 Mb/s full duplex로 협상되는지 확인합니다.

```bash
sudo ethtool enp1s0
sudo ethtool enp2s0
```

관리적으로 내려간 포트는 **시험 장비의 해당 포트임을 확인한 뒤** 사용자가 올릴 수 있습니다. 원래 상태를 기록해 두고 검사 후 복원하세요. 이는 아래 도구가 자동 실행하는 작업이 아닙니다.

```bash
sudo ip link set dev enp1s0 up
sudo ip link set dev enp2s0 up
```

IP 주소를 새로 설정할 필요는 없습니다. 같은 호스트의 IP 주소끼리 `ping`/`iperf3`를 실행하면 물리 케이블을 거치지 않는 경우가 있으므로, 이 도구는 **실제 인터페이스에서 실험용 이더넷 프레임(EtherType 0x88B5)을 송신하고 상대 인터페이스의 수신을 확인**합니다. 자신이 보낸 패킷의 송신 복사본은 수신 성공으로 세지 않습니다. 순번과 실행별 식별자, 페이로드 체크섬으로 손실·중복·순서 변화·데이터 오류를 구분합니다. 패킷 내용 자체는 파일에 저장하지 않습니다.

### C. 낮은 부하에서 시작한 뒤 올리기

첫 명령은 사전 검사만 합니다. 실제 송신은 `--run`이 있어야 시작합니다. 아래는 각 방향당 10 Mb/s, 60초 검사입니다.

```bash
sudo python3 wire_test.py --interfaces enp1s0 enp2s0 --duration 60 --mbps 10
sudo python3 wire_test.py --interfaces enp1s0 enp2s0 --duration 60 --mbps 10 --run
```

정상이면 100 Mb/s, 300 Mb/s처럼 단계적으로 부하를 높입니다. 아래는 양방향 각각 300 Mb/s, 30분 검사입니다. 각 방향의 속도이며 두 방향의 합계가 아닙니다. 10/100/300 Mb/s 수치는 초기 점검 예시이고, 제품 사양이나 실제 카메라 트래픽을 대신하는 합격 규격은 아닙니다.

```bash
sudo python3 wire_test.py --interfaces enp1s0 enp2s0 \
  --duration 1800 --mbps 300 --run
```

Python·CPU·소켓 수신 버퍼 한계로 목표 속도에 도달하지 못하거나 검사 프로그램 자체의 수신 버퍼에서 드롭이 발생하면 **판정 불가**로 표시합니다. 속도를 낮춰 재검사하고, 실제 선속도에 가까운 규격 검사가 필요하면 별도 PC의 `iperf3` 또는 전문 시험기를 사용하세요. 여기서 표시하는 wire Mb/s는 FCS·프리앰블·IFG를 포함한 계산값이며 외부 계측기로 측정한 값은 아닙니다.

### D. 모든 포트와 공통 자원 확인

| 순서 | 연결 | 확인 목적 |
|---|---|---|
| 1 | P1 ↔ P2 | 두 포트와 공통 컨트롤러 경로 |
| 2 | P3 ↔ P4 | 다른 두 포트 |
| 3 | P1 ↔ P5 | 다섯 번째 포트 포함 |
| 4 | P1 ↔ P2와 P3 ↔ P4를 동시에 | 공통 PCIe·인터럽트·전원·열 조건에서 복합 부하 |

4번은 서로 겹치지 않는 포트 쌍을 별도 터미널에서 검사합니다. 이때 세 번째 카메라 포트까지 동시에 부하를 줄 수 있습니다. 정상 케이블을 교체하면서 불량이 케이블을 따라가는지, 특정 포트에 남는지 확인하세요. 포트 쌍 검사만으로 어느 쪽 포트가 불량인지 확정하지 말고 상대 포트를 바꿔 교차 확인합니다.

낮은 부하 검사 후 문제가 없으면 고객이 보고한 고장 발생 시간 이상 장시간 검사합니다. 시간 정보가 없으면 8~24시간을 초기 관찰 시간으로 잡을 수 있으나, 하루 통과가 간헐 불량을 배제하지는 않습니다. 같은 검사 조건을 정상 기준 장비에서도 실행해 비교하면 유용합니다.

CPU 부하와 결합할 필요가 있으면 먼저 기록과 LAN 시험을 켜고, 별도 터미널에서 선택적으로 다음 정도부터 시작합니다. 장비 냉각 조건과 제조사 허용 온도를 지키며 온도·주파수 제한·OOM 로그를 확인하세요. 이 명령은 자동 실행하지 않습니다.

```bash
sudo apt-get install -y stress-ng
stress-ng --cpu 0 --cpu-load 60 --timeout 10m --metrics-brief
```

전원 점검은 제품에 공급되는 전압과 실제 부하 조건을 기준으로 합니다. 의심 시 규격에 맞는 정상 전원 장치로 교차 확인하고, 가능하면 부하 중 전압·리플을 계측합니다. 소프트웨어만으로 전원 이상을 배제할 수 없습니다. 카메라 전원·PoE 부하가 없는 검사는 해당 부하 조건을 재현하지 못합니다. 임의의 부하나 잘못된 PoE 전원 연결로 대신하지 마세요.

## 3. 결과 해석

실행마다 별도 디렉터리가 생기고 `wire_test.py`의 결과는 `summary.json`에 저장됩니다.

| 결과 | 의미 | 종료 코드 |
|---|---|---|
| `PASS_FOR_THIS_WIRE_TEST_ONLY` | 목표의 80% 이상 송신 속도, 관측된 손실·포트 이상 없음. 이 시험 조건에 한정 | 0 |
| `ANOMALY_OBSERVED` | 손실·순서 변화·송수신 오류 또는 NIC 변화가 관측됨. 장비 불량 확정은 아님 | 1 |
| `INCONCLUSIVE…` | 사용자 중단, 검사기 수신 드롭, 송신 속도 부족, 수집 오류 등으로 판정 불가 | 2 |

사전 검사만 성공한 종료 코드 0은 송수신 시험 통과가 아닙니다. 검사 중 케이블을 뽑으면 해당 실행은 의도된 이상이 기록됩니다. 이 방법으로 로그 검출을 검증한 실행과 정상 조건 합격 판정용 실행은 분리하세요. 물리 연결 단절이나 카운터 초기화를 정상으로 숨기지 않습니다.

장시간 기록 요약은 출력된 `run-…` 디렉터리를 지정합니다. `sudo`로 수집한 결과는 조회에도 같은 권한이 필요할 수 있습니다.

```bash
sudo python3 lan_diag.py report ./lan-diag-logs/run-실제디렉터리 > report.json
```

`report`는 보존 중인 로그의 이벤트를 요약하며 마지막 2,000개 이벤트 상세와 전체 이벤트별 개수를 출력합니다. 종료 코드 0은 로그에 읽을 수 있는 샘플이 있다는 뜻이고, 제품 합격 판정이 아닙니다. `system_log`, `nic_detail`, 시작·종료 스냅샷도 확인해야 합니다. 벤더별 상세 NIC 카운터의 의미는 드라이버 문서와 비교하세요.

| 관측 | 우선 조사할 항목 |
|---|---|
| 여러 포트의 `carrier`가 함께 내려가거나 드라이버가 리셋됨 | 공통 전원, 랜 칩, PCIe, 보드, 열, 드라이버·펌웨어 |
| 특정 포트의 CRC·프레임 오류 증가 | 케이블·커넥터·포트·노이즈. 케이블 교차 검사로 좁힘 |
| 링크 유지, `rx_missed_errors`·FIFO·드롭 증가 | 수신 버퍼, CPU/인터럽트 병목, 드라이버. 카운터 의미는 드라이버마다 다름 |
| `softnet_pressure`와 CPU 한 코어의 높은 사용률 | 호스트 패킷 처리 여유, IRQ/RSS/큐 배치. 설정 변경 전에 기준 로그 확보 |
| 포트 시험은 정상인데 현장에서 세 카메라만 함께 중단 | 공유 카메라 전원·트리거, SDK 공통 처리 스레드, 프로그램 교착·버퍼 누수, 실제 영상 패킷 부하 |
| 선별용 PC 연결까지 함께 끊김 | 카메라 개별 고장보다 시스템 전체·공통 NIC 자원 문제부터 조사 |

한 가지 관측으로 원인을 확정하지 마세요. `rx_dropped`나 softnet 드롭은 케이블 단선만을 의미하지 않습니다. 커널 로그에서 `NETDEV WATCHDOG`, `reset`, `timeout`, `AER`, `PCIe`, `link down`, `thermal`, `Out of memory` 등의 전후 문맥을 확인하세요.

## 4. 카메라 없는 검사로 확인할 수 없는 것

- 실제 카메라의 고장, 카메라 발열, 카메라 전원·PoE 부하, 현장 케이블·접지·인버터 노이즈.
- 카메라의 영상 패킷 크기·전송 간격·트리거에 따른 버스트와 정확히 같은 조건.
- GigE Vision/GVSP/GVCP·UDP/IP 경로와 제조사 SDK의 재접속·버퍼 누수·스레드 교착. 기가비트 이더넷 연결이라는 정보만으로 GigE Vision 사용을 단정할 수 없습니다.
- 3대 카메라가 실제로 함께 영상 전송할 때만 발생하는 프로그램·펌웨어 결함.

`wire_test.py`는 원시 Ethernet 경로를 검사합니다. IPv4/UDP 스택 전체나 실제 영상 획득을 재현하는 카메라 시뮬레이터는 아닙니다. 더 깊은 네트워크 검사는 시험용 PC와 `iperf3`로 TCP/UDP를 단계적으로 검사하고, 영상 단계 검사는 해당 모델의 카메라·제조사 도구/지원되는 시뮬레이터로 진행해야 합니다.

**입고 시 재현되지 않으면 현장 장비에서 장애 전후 기록을 남기는 것이 필요합니다.** 재부팅하면 장애 당시 상태가 사라질 수 있으므로, 가능하면 로그를 먼저 보존합니다. 안전한 정지 절차를 우선하고 카메라·선별 프로그램 로그와 진단 로그의 시각을 맞춰 수집하세요. 모든 로그의 시각은 UTC이며 `+00:00`으로 표시됩니다. 한국 표준시는 9시간을 더해 비교합니다. 단조 증가 시간도 함께 저장하므로 시스템 시각 보정과 실제 시간 간격을 구분할 수 있습니다.

## 5. 현장 장비의 카메라/PC 응답 기록 (선택)

`targets.example.json`을 `targets.local.json`으로 복사하고 실제 포트 이름·IP를 입력합니다. 예시 IP는 장비에 적용할 네트워크 설정이 아니며 실제 주소로 바꿔야 합니다. 서로 다른 물리 NIC에 같은 서브넷을 중복 설정했는지, IP 충돌·카메라 서브넷·라우팅이 올바른지도 함께 확인하세요. 도구가 이를 자동 수정하지는 않습니다.

```bash
cp targets.example.json targets.local.json
sudo python3 lan_diag.py monitor \
  --interfaces enp1s0 enp2s0 enp3s0 enp4s0 enp5s0 \
  --config targets.local.json --active-probes \
  --duration 86400 --output ./lan-diag-logs
```

`--active-probes`가 있으면 대상당 매 주기에 Ping 1회를 지정 NIC에 묶어 실행합니다. `tcp_port`를 명시한 대상만 추가 TCP 연결을 시도합니다. **GigE 카메라가 TCP를 쓴다고 가정하지 마세요.** 해당 서비스가 연결을 받아도 되는지 확인하고 필요한 경우에만 포트를 설정합니다. 바인딩 권한이 없으면 다른 NIC로 우회하지 않고 수집 불가를 기록합니다. Ping 미응답은 ICMP 차단·미지원 때문일 수도 있으며 영상 중단의 확정 증거가 아닙니다.

영상 수신 중단을 확인하려면 기존 프로그램 또는 지원되는 SDK 수신기에서 **정상 프레임을 수신했을 때만** 갱신되는 파일을 연결할 수 있습니다.

```json
{
  "targets": [
    {
      "name": "vision-1",
      "interface": "enp2s0",
      "ip": "192.168.20.10",
      "heartbeat_file": "/run/camera-health/vision-1.last-frame",
      "max_age_seconds": 5
    }
  ]
}
```

진단 도구는 파일의 수정 시각을 읽기만 합니다. 파일을 만드는 SDK 연동은 포함하지 않습니다. 생존 타이머가 파일을 갱신하면 영상이 없어도 정상으로 잘못 보일 수 있습니다. 트리거 대기 시간이 긴 정상 운전이라면 영상이 없는 시간을 장애로 오인하지 않도록 임계 시간을 맞추고, 연결 세션 상태와 프레임 타임아웃을 따로 해석하세요.

## 6. 로그 보관과 프로그램 검증

- 실행별 telemetry 기본 보관량은 10 MiB × 10파일, 약 100 MiB입니다. 오래된 로그는 순환 삭제되며 보존 범위 밖의 사건은 보고서에 나오지 않습니다. `--log-mb`, `--backups`로 조정할 수 있습니다.
- 시작·종료 스냅샷은 별도입니다. 실행 디렉터리는 자동 삭제하지 않으므로 반복 검사 시 전체 디스크 여유를 관리하세요. 전원 차단 시 마지막 일부 기록이 사라질 수 있습니다. 주기마다 전원 차단까지 보장하는 동기 쓰기를 하지는 않습니다.
- 결과에는 IP·MAC·호스트 정보와 커널 로그가 들어갈 수 있습니다. 외부 전달 전에 내용을 검토하세요. 실행 디렉터리는 기본 권한 0700이며 관리자 권한 수집 결과의 접근 권한을 무분별하게 풀지 마세요.
- `lan_diag.py --duration`은 수집 반복 구간의 시간입니다. 시작·종료 스냅샷 및 진행 중인 응답 검사 때문에 전체 실행 시간은 더 길 수 있습니다. 대상이 많거나 느리면 간격이 늘어날 수 있고 `sampling_delay`가 기록됩니다.

개발 검증:

```bash
python3 -m unittest discover -s tests -v
```

프레임 검증, 손실·중복·순서 처리, 포트 교체·카운터 초기화, 로그 순환, 권한 부족, Ping 실패와 수집 불가 구분 등을 검증합니다. raw socket 권한이 없으면 루프백 프레임 통합 시험은 skip됩니다. 루프백 시험 통과 역시 실제 케이블·NIC 검증을 대신하지 않습니다.
