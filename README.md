# Ubuntu 골프 센서 장비 입고 진단

대상: Intel i5-1335U / DDR5 8 GB / NVMe 250 GB / 10G LAN 1개 / 2.5G LAN 2개 / 1G LAN 2개 / USB-A 4개.

현장 구성은 10G에 스핀센서, 2.5G 두 포트에 골프존 에코센서, 1G 한 포트에 게임 PC를 연결하는 방식입니다. 게임 도중 “센서연결 끊김”으로 진행이 불가능하지만, 입고 후에는 재현되지 않는 상황을 조사합니다. 입고 검사 시 실제 센서를 연결할 수 없다는 조건으로 제작했습니다.

**센서 없이도 발열·CPU/메모리/스토리지 병목·PCIe/드라이버 오류·LAN 단절을 관찰하고 재현 조건을 좁힐 수 있습니다. 이 프로그램은 실제 카메라, 제조사 SDK, 골프존 게임이나 센서 프로토콜을 모사하지 않습니다. 무센서 검사 통과가 제품 전체 정상이라는 의미는 아닙니다.**

## 가장 먼저 확인할 점

M.2는 장착 형식이고 여기서 검사하는 저장장치는 NVMe입니다. NVMe 온도가 높다는 사실만으로 통신 끊김의 원인이 확인되지는 않습니다. 온도가 올라간 시간, NVMe 응답 지연/리셋, PCIe 오류, NIC 링크/드롭, 게임·센서 수신기의 오류를 같은 시간축에서 비교해야 합니다. 1G 게임 PC 연결이나 공통 처리 프로그램이 멈춰도 화면에 센서 연결 오류가 표시될 수 있으므로 이 경로도 함께 확인합니다.

| 관측되는 증거 | 다음 조사 |
|---|---|
| 여러 LAN의 carrier가 함께 내려가거나 장치가 사라짐 | 공통 전원·PCIe·NIC/드라이버·보드·열 조건 |
| carrier 유지, CRC/프레임 오류 증가 | 현장 케이블·접점·노이즈·포트 교차 검사 |
| carrier 유지, 수신 드롭·FIFO·softnet 증가, 특정 CPU 코어 포화 | 수신 처리 여유·IRQ/큐·메모리/버퍼·드라이버 |
| NVMe 온도 상승과 함께 I/O 지연·timeout/reset·SMART/PCIe 변화 | 저장장치·공통 PCIe·전원·냉각을 우선 조사. 온도와 원인을 동일시하지 않음 |
| 하드웨어 지표가 유지되는데 게임에서만 끊김 | 1G 제어 연결·SDK·공통 수신 스레드·메모리 누수·교착·실제 센서 전원/트리거 |

동일한 설정·작업에서 제조사 허용 범위 안의 냉각 조건만 바꿔 반복하고, 정상 기준 장비와 비교하세요. 냉각을 개선했을 때 문제가 줄면 열 관련 가능성을 좁힐 수 있지만 NVMe 단독 고장이라고 확정하지는 못합니다. 팬 막기·보호 한도 해제·임의의 히터로 과열시키는 방식은 사용하지 않습니다. 케이스 조립 상태, 설치 방향, 실내 온도, 팬·먼지, 전원 장치, BIOS/커널/NIC·NVMe 펌웨어, 케이블 길이를 현장과 맞추는 것이 중요합니다.

## 구성과 설치

Python 3.8 이상과 Ubuntu 20.04 이상에서 동작하도록 작성했습니다. 하드웨어에 대한 Ubuntu/커널 지원 여부는 제조사가 검증한 버전으로 확인하세요. 도구는 BIOS·드라이버·MTU·IP·EEE·ASPM·IRQ·전원 정책을 자동 변경하지 않습니다.

| 프로그램 | 역할 |
|---|---|
| `sensor_lab.py inventory` | CPU·저장장치·NIC 모델/드라이버·USB 트리·라우팅·온도·SMART 스냅샷 |
| `sensor_lab.py monitor` | 읽기 위주의 장시간 기록. 센서/케이블 없이도 실행 가능 |

```bash
git clone https://github.com/soriel1004/linux-test.git
cd linux-test

```

관리자 권한을 사용하면 커널 로그·NIC 상세 통계·NVMe SMART를 더 완전하게 수집할 수 있습니다. 패키지 설치 시 서명/TLS 검증을 해제하지 않으며 `sensors-detect` 같은 하드웨어 탐지 명령은 자동 실행하지 않습니다.

## 1. 포트·온도·저장장치 확인

```bash
sudo python3 sensor_lab.py inventory > inventory.local.json
ip -br link
ip -br address
sensors
sudo nvme list
df -h / /var/tmp
```

포트의 실물 위치와 우분투 이름을 대응시켜 기록하세요. 아래 이름은 예시입니다.

| 실물 포트 | 용도 | 우분투 이름 (직접 기록) |
|---|---|---|
| 10G | 스핀센서 | 예: enp1s0 |
| 2.5G A | 에코센서 1 | 예: enp2s0 |
| 2.5G B | 에코센서 2 | 예: enp3s0 |
| 1G A | 게임 PC | 예: enp4s0 |
| 1G B | 여분 | 예: enp5s0 |

인터페이스 이름만으로 속도를 추정하지 않습니다. `ethtool 포트이름`의 지원 모드와 실제 Link detected/Speed를 구분하세요. 케이블이 없는 포트의 carrier=0이나 speed 미상은 정상적인 미연결 상태일 수 있습니다.

CPU(`coretemp` 등)와 NVMe(`nvme`) 온도가 실제로 읽히는지 확인합니다. Intel CPU 온도가 없으면 제조사 지원 커널/드라이버를 먼저 확인하고, 필요 시 관리자가 `sudo modprobe coretemp`를 검토할 수 있습니다. 온도가 없다고 0°C로 처리하지 않습니다. CPU 또는 NVMe 온도가 수집되지 않으면 읽기 기록은 가능하지만 능동 부하 시험은 시작하지 않습니다.

## 2. 무부하 기준 기록

케이스를 실제 사용 상태로 조립하고 30분 정도 기준 기록을 남깁니다.

```bash
sudo python3 sensor_lab.py monitor --duration 1800
```

처음에는 모든 물리 Ethernet을 자동 선택합니다. 물리 포트가 없는 개발 컨테이너에서는 비루프백 NIC로 대체합니다. 특정 포트를 지정할 수도 있습니다.

```bash
sudo python3 sensor_lab.py monitor \
  --interfaces enp1s0 enp2s0 enp3s0 enp4s0 enp5s0 \
  --duration 86400 --interval 2
```

`--duration 0`은 Ctrl+C/SIGTERM까지 기록합니다. 시작·종료 인벤토리와 명령 타임아웃 때문에 실제 전체 시간은 지정한 수집 시간보다 길 수 있습니다. 기록 중 네트워크 설정이나 영상 데이터를 전송하지 않습니다. 인벤토리나 선택적인 SMART 조회 자체는 장치에 읽기 명령을 보냅니다.

기록 항목은 CPU/NVMe 온도·센서별 critical 값, CPU 전체/코어별 사용률·열 제한 횟수, 가용 RAM/메모리 및 I/O pressure, NVMe 디스크 처리량·평균 I/O 시간, SMART, PCIe AER, NIC 링크·오류·드롭, softnet, 커널·USB 연결 관련 로그입니다. SMART와 상세 NIC 통계는 약 30초마다 별도 작업으로 수집합니다. 권한·명령·커널 기능이 없으면 해당 항목은 수집 불가로 남습니다. 시작 전에 존재한 SMART 오류는 새로 발생한 오류와 구분합니다.

## 3. 원인을 나누는 부하 시험

생산망과 분리한 입고 검사 장비에서 진행합니다. 먼저 CPU만, 다음 RAM만, NVMe만, LAN만 확인하고 각 단계 사이에 기준 온도로 돌아오는지 관찰하세요. 정상 기준 장비에서도 같은 조건을 반복합니다. 아래 값은 초기 점검 예시이며 제품의 공식 합격 규격이 아닙니다.

### CPU와 메모리

```bash
# CPU: 2개 worker, worker당 목표 60%, 10분
sudo python3 load_test.py --cpu --workers 2 --cpu-load 60 --duration 600

# RAM: 가용 메모리를 확인한 뒤 512 MiB, 10분
sudo python3 load_test.py --memory-mb 512 --duration 600
```

CPU worker 수는 논리 CPU 기준이며 P/E 코어에 고정하지 않습니다. 처음부터 12스레드를 모두 최대로 점유하지 않고 2 → 4 → 6개처럼 올려 비교하세요. CPU 부하는 stress-ng가 보고하는 목표치이고 전체 시스템 CPU 사용률과 같지 않습니다. RAM 시험은 가용 메모리의 25%를 넘기면 시작하지 않으며, 가용 RAM 256 MiB 미만이면 시험을 중단합니다. 이 폴링 방식이 모든 OOM을 예방할 수 있는 것은 아닙니다.

### NVMe 파일 I/O

```bash
# /var/tmp가 실제 NVMe 파일시스템 위에 있을 때
sudo python3 load_test.py --disk-dir /var/tmp --disk-size-mb 256 \
  --disk-mib 8 --duration 600
```

대상 디렉터리는 기존 디렉터리여야 하며 findmnt/lsblk로 NVMe의 파티션 또는 LVM 경로인지 확인합니다. tmpfs·overlay·네트워크 저장장치 등에서는 NVMe 시험으로 진행하지 않습니다. 블록 장치에 직접 쓰거나 기존 사용자 파일을 덮어쓰지 않고 전용 임시 파일만 최대 지정 크기로 순환 덮어씁니다. 파일별 fsync와 캐시 반환 힌트를 사용하며 시스템 전체 page cache는 비우지 않습니다. 최소 2 GiB와 파일 크기의 두 배 이상 여유 공간을 요구하고 시험 중 1 GiB 미만이면 중단합니다.

**쓰기 시험은 SSD 쓰기 수명을 사용합니다.** 기본 8 MiB/s × 600초는 약 4.7 GiB의 요청 쓰기량이며 실제 장치 쓰기 증폭은 별도입니다. 기본 파일 점유 크기는 256 MiB입니다. 중요한 데이터는 보존하고 제조사 허용 조건에서 짧게 시작하세요. 정상 종료 시 임시 파일을 제거하고, 커널 I/O가 멈춰 프로세스가 종료되지 못하면 잔여 경로를 결과에 남깁니다. 임의의 사용자 파일은 삭제하지 않습니다.

### 공통 온도·상태 중단 기준

- CPU 85°C, NVMe 70°C를 기본 **시험 중단 기준**으로 사용합니다. 제품 불량 판정 온도가 아닙니다.
- 커널에서 읽은 센서의 critical 값이 있으면 그보다 5°C 낮은 값과 사용자 기준 중 더 낮은 값을 적용합니다.
- CPU/NVMe 온도 수집 불가·기준 도달, NVMe critical_warning, RAM 부족, PCIe AER/새 NVMe 오류 증가, 작업 프로세스의 조기 종료 시 중단/판정 불가로 기록합니다.
- `--cpu-limit`(50~95°C), `--nvme-limit`(40~80°C)로 조절할 수 있지만 제조사 한도는 별도로 지켜야 합니다. SMART 경고가 단순히 온도 경고라는 뜻은 아니며 원본 SMART를 확인해야 합니다.
- 약 1초 간격의 소프트웨어 중단입니다. 급격한 온도 상승·호스트 전체 정지·커널 I/O 대기 상황까지 제어하는 하드웨어 보호 장치는 아닙니다. 제조사 냉각·보호 장치를 유지하고 감독하에 검사하세요.

결과는 `load-result.json`에 기록됩니다. `COMPLETED_OBSERVATION`은 지정한 관찰 시간이 끝났다는 뜻으로 제품 전체 합격이 아닙니다. 중단 사유와 작업 종료 코드는 별도 기록합니다.

## 4. 카메라 없는 LAN 시험

정상 확인된 짧은 Cat6A 케이블로 **제품의 두 LAN 포트를 직접 연결**합니다. 포트는 standalone이어야 하며 브리지·본딩에 속한 포트와 기본 경로가 잡힌 관리 포트는 거부합니다. 기본 경로 검사만으로 모든 원격 관리 연결을 알 수는 없으므로 반드시 로컬 콘솔에서 시험 포트를 확인하세요. 도구는 포트를 올리거나 IP/MTU를 바꾸지 않습니다. 필요한 경우 검사자가 해당 포트임을 확인한 뒤 `sudo ip link set dev enp2s0 up`처럼 올리고 원래 상태를 기록합니다.

권장 쌍은 2.5G A ↔ 2.5G B, 1G A ↔ 1G B입니다. 10G 포트는 여분 1G/2.5G 포트 또는 별도 테스트 PC로 교차 확인합니다.

**10G 포트와 2.5G 포트를 연결하면 서로 지원하는 낮은 속도로 협상됩니다.** 일부 10G NIC는 2.5G 모드를 지원하지 않아 1G로 협상될 수도 있습니다. 10G 포트가 하나인 이 제품만으로 10G 상대와의 정상 동작을 검증할 수는 없습니다. 별도 10G NIC/테스트 PC 또는 계측기가 필요합니다.

```bash
# 포트 이름을 실제 값으로 바꾸세요. 첫 명령은 송신하지 않는 사전 검사.
sudo python3 wire_test.py --interfaces enp2s0 enp3s0 --mbps 50 --duration 60
sudo python3 wire_test.py --interfaces enp2s0 enp3s0 --mbps 50 --duration 60 --run

# 초기 검사 후 각각 200 Mb/s, 10분 관찰
sudo python3 wire_test.py --interfaces enp2s0 enp3s0 --mbps 200 --duration 600 --run
```

각 방향당 속도입니다. IP 로컬 라우팅을 우회해 물리 송신 경로에서 실험용 Ethernet 프레임(0x88B5)을 보내고 상대 포트에서 실행 ID·순번·페이로드 CRC를 확인합니다. 송신 복사본은 수신 성공에서 제외합니다. IP를 임시로 설정하지 않으며 다른 장치에 연결된 상태로 실행하지 않습니다. CPU/NVMe 온도와 RAM 중단 기준도 적용합니다.

| 결과 | 의미 |
|---|---|
| `NO_ANOMALY_AT_THIS_RATE` | 이번 협상 속도·실제 달성 부하에서 이상을 관찰하지 않음 |
| `ANOMALY_OBSERVED` | 손실·순서 변화·NIC/시스템 지표 변화 등 관측. 어느 부품 불량인지 확정 아님 |
| `INCONCLUSIVE…` | 검사기 수신 드롭·목표 부하 미달·온도 중단·권한/프로세스 문제·사용자 중단 등 |

`wire-result.json`의 실제 송신 속도·손실·수신 소켓 드롭·협상 속도를 함께 보세요. Python 프로그램의 CPU/소켓 처리 한계로 2.5G/10G 선속도를 달성하지 못할 수 있습니다. 목표의 80%에도 도달하지 못하면 속도 미달로 구분합니다. 표시 wire Mb/s는 Ethernet overhead를 포함한 추정값이며 외부 계측값은 아닙니다.

이 원시 Ethernet 시험은 **GVSP/GVCP·UDP/IP·실제 영상 버스트·SDK를 재현하지 않습니다.** 선속도/UDP 수신 버퍼 검증에는 독립된 상대 PC와 `iperf3` 또는 전용 트래픽 장비를 사용하고, 카메라 프로토콜 검사에는 실제 센서 또는 제조사가 제공하는 호환 시뮬레이터가 필요합니다. 같은 PC의 IP 두 개끼리 iperf를 실행하면 케이블을 거치지 않는 경우가 있으므로 독립된 상대를 사용해야 합니다.

정상 케이블과 정상 상대 포트를 바꾸면서 문제가 케이블을 따라가는지 특정 포트에 남는지 구분합니다. 쌍 검사만으로 어느 포트가 고장인지 확정하지 않습니다. USB 4포트는 커널 로그/트리 확인 대상이며 실제 USB 기기 없이 데이터·전원 정상 여부를 판정하지 않습니다.

## 5. 마지막에 복합 부하

단독 시험 이후 온도·공간 여유가 있을 때만 실행합니다. 한 터미널에서 CPU/RAM/NVMe를 실행하고 다른 터미널에서 LAN 시험을 병행할 수 있습니다.

```bash
sudo python3 load_test.py --cpu --workers 4 --cpu-load 70 --memory-mb 512 \
  --disk-dir /var/tmp --disk-mib 8 --duration 600
```

각 프로그램의 온도 가드가 자기 작업을 중단하며, 호스트나 다른 프로그램을 재부팅·종료하지 않습니다. 로그는 실행별로 분리됩니다. 복합 시험에만 이상이 나타나면 전원·공유 PCIe·CPU 코어/인터럽트·케이스 온도 등 공통 조건을 비교하세요. 전원·접지·현장 노이즈는 소프트웨어만으로 배제할 수 없어 규격에 맞는 정상 전원 장치 교차 검사와 필요 시 계측이 필요합니다.

30분 시험만으로 간헐 불량이 배제되지는 않습니다. 현장 고장 발생 시간을 넘는 관찰(정보가 없으면 8~24시간의 수동 기록부터)을 하고, 온도가 회복되는 휴지 기간을 두며 반복합니다. 능동 부하의 1회 최대 시간은 1시간으로 제한했습니다. 무작정 하루 동안 SSD 쓰기/고부하를 지속하는 기본 동작은 없습니다.

## 6. HTML 보고서와 보관

실행 시 표시한 **해당 실행 디렉터리**를 지정합니다.

```bash
sudo python3 sensor_lab.py report ./results/monitor-실제디렉터리
```

같은 폴더에 `report.html`, `report.json`이 생성됩니다. HTML은 인터넷 없이 브라우저에서 열 수 있으며 CPU·NVMe 온도 추이, NIC/NVMe/PCIe 이벤트 시각, 온도 최고값·코어 사용률·가용 RAM·디스크 평균 I/O 시간·NIC 카운터 증가, 커널 오류 관련 키워드 일치 항목을 보여줍니다. 보고서 생성 성공은 장비 합격이 아닙니다. 커널 키워드 일치도 오류 원인의 자동 판정이 아니며 전후 원본 로그를 읽어야 합니다. 디스크 await는 각 표본 구간의 평균이며 개별 I/O 최댓값을 측정하는 값은 아닙니다.

온도·카운터 값이 없으면 unknown/null로 남습니다. 드롭/오류 카운터는 겹쳐 집계될 수 있어 합을 실제 손실 패킷 수로 해석하지 않습니다. PCIe AER는 시스템 전체 장치의 카운터이며 NIC/NVMe 관련 장치인지 lspci와 NIC 장치 경로를 대조하세요. 일부 커널/드라이버는 해당 카운터나 온도를 제공하지 않습니다.

로그는 기본 실행당 10 MiB × 20파일(약 200 MiB)로 순환 저장합니다. 보고서는 **현재 보존 중인 구간만** 요약하므로 24시간 명령을 실행했다고 반드시 24시간 전체가 남는 것은 아닙니다. 장시간 시험은 중간에도 결과를 보존하세요. 인벤토리/보고서/작업 로그는 별도이며 실행 디렉터리 전체는 자동 삭제하지 않습니다. 반복 검사 시 디스크 여유를 관리하세요. 정전 시 마지막 일부 로그가 사라질 수 있습니다.

시각은 UTC(+00:00), 한국 표준시는 +9시간입니다. 단조 증가 시간도 남겨 OS 시각 보정과 시간 간격을 구분합니다. 로그에는 IP/MAC·장치 정보·커널 메시지가 포함될 수 있어 외부 전달 전 내용을 검토하세요. 디렉터리 권한은 0700이며 root로 수집했으면 조회/복사에도 해당 권한이 필요할 수 있습니다.

## 7. 현장에서만 발생할 때 꼭 남길 것

무센서 입고 시험으로 재현되지 않으면 **현장 장애 직전/직후의 읽기 기록과 게임·센서 수신기 로그**가 필요합니다. 재부팅 전에 안전한 절차로 로그를 확보하고 다음을 같은 시각으로 남기세요.

1. 센서 3개와 게임 PC 1G 링크 중 무엇이 실제로 끊겼는지, 포트 LED·carrier·ping/제어 채널·프레임 수신 상태.
2. 제품 온도·케이스 외부 온도·팬 상태, NVMe reset/timeout·PCIe·NIC 드라이버·OOM 전후 로그.
3. SDK 오류 코드/마지막 정상 프레임 시각/재연결 결과·프로세스별 CPU/RAM 증가. 단순 Ping 정상만으로 영상 정상이라 판단하지 않음.
4. 정상·불량 장비의 NIC 칩셋/드라이버, NVMe 모델/펌웨어, BIOS·Ubuntu 커널 버전, 전원·케이블·설치 환경 비교.

실제 센서 전원·동기 트리거, 영상 버스트, SDK 공통 수신 스레드, 게임과의 프로토콜을 검사하려면 센서 또는 지원되는 시뮬레이터가 최종적으로 필요합니다. 그 한계를 지키면서 이 도구로 하드웨어·호스트 자원 문제를 먼저 좁히는 것이 목적입니다.
